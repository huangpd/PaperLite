# PaperLite 自动化识别与分阶段调度架构方案 (Staged Pipeline Architecture)

> **设计基石**：拒绝“边跑边动态探查、动态改表”的高风险黑盒模式。对于千万级的大规模采集，稳健性压倒一切。系统采用**三阶段流水线解耦架构（Staged Pipeline Architecture）**：**先映射建档 ➜ 再体检定级 ➜ 最后确定性大生产**。

---

## 二、详细技术拆解

### 阶段一：映射建档（Resolve - DuckDB 向量化引擎驱动）
* **核心目标**：绝不靠生拼硬凑猜测域名，采用 DuckDB 向量化 OLAP 引擎秒级完成千万至亿级数据的分类聚合与抽样，并用最轻量的网络代价，把海量论文全部打上真实的出版商落地域名标签。
* **算法实现**：
  1. **DuckDB 极速向量化聚类抽样 (`DuckDBClusterer`)**：
     - 直接在 C++ 向量化引擎内执行正则聚合，单表 195 万条数据仅需 **0.22 ~ 0.43 秒** 即可收敛为 3,548 个独立族群。
     - 自动持久化至 SQLite 主库的 `doi_clusters` 表，记录各族群总论文量与代表样本 DOI。
  2. 针对多出版商大类与二级期刊正则规则：
     - `10.1016/j.ajog.*` ➜ 提取特征 Key `10.1016/j.ajog`
     - `10.1016/0002-9378.*` ➜ 提取特征 Key `10.1016/0002-9378`
     - `10.1002/adma.*` ➜ 提取特征 Key `10.1002/adma`
     - 其他出版商 ➜ 提取顶级/二级代码（如 `10.1109`, `10.1038`）
  3. 每个特征 Key 仅抽取 1 条代表样本（`sample_doi`）；
  4. 通过异步 HTTP GET/HEAD（跟随 302 重定向与 Meta-Refresh，不读多余主体）跑出真实 `final_host`；
  5. 将映射关系持久化至 SQLite 主库的 `doi_domain_routes` 表。

### 阶段二：模式体检与裁决（Audit）
* **核心目标**：彻底消除黑盒不确定性，在开跑前查清每一个出版商站点的底细。
* **反假空壳机制（双视角差分核验）**：
  1. 浏览器跑出文章真值（真实标题、摘要核心句、真实文本量）；
  2. cURL 发送模拟请求；
  3. 比对标题与摘要内容：
     - 若 cURL 仅返回通用占位标题（如 `Loading...` 或单一网站名）或正文极短，认定为 **SPA 客户端渲染空壳**；
     - 判定为 `browser-only`，绝不允许假空壳数据污染数据盘；
  4. 比对 Cloudflare / WAF 行为：
     - 若无盾且内容真实 ➜ `curl-direct`；
     - 若能复用 `cf_clearance` 且内容真实 ➜ `curl-pool`（如 ACM）；
     - 若动态拦截或不发 clearance ➜ `browser-only`（如 ScienceDirect / Cell）。
* **产出物**：
  - 终端结构化报表；
  - 固化配置文件 `domain_rules.toml`（允许人工审查或微调）。

### 阶段三：大规模精准分流执行（Run）
* **核心目标**：大生产环境零多余开销，各司其职，极速稳定。
* **运行机制**：
  1. 内存载入 `domain_rules.toml` 作为只读快照；
  2. 每一篇 DOI 进任务队列时瞬间命中对应通道：
     - `curl` 渠道任务：汇入高并发轻量下载线程；
     - `browser` 渠道任务：汇入 `BrowserPool`；
  3. 浏览器工作线程实行**域名粘滞（Domain Affinity）**：
     - 绑定当前域名连续处理（如 30~50 篇切片）；
     - 充分利用已过盾的浏览器环境与代理 IP 寿命；
     - 遇到卷期结束或切片满额，平滑轮转下一个同域名批次。
